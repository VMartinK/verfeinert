## Immutable Scientific Contract

The v0.4.0 implementation plan does not require changing the frozen scientific
semantics:

- expressibility remains `E = -log10(D_KL)`;
- trainability keeps the v0.3.2 Local-X semantics and visualization label
  `T(H)`;
- structural-cost component, normalization, and weighting semantics are
  preserved;
- Pareto dominance, strict Pareto behavior, ranking, and strict feedback
  semantics are preserved;
- the approved publication visualization contract remains frozen;
- F/F2 remain out of contract.

Any future implementation step that would require changing one of these
contracts must stop as a release blocker.

## Current Architecture Summary

`ansatz_generator` already owns canonical candidate construction,
ConstraintSet records, Sanz19 candidate generation, staged-package export, and
an insert-gate mutation factory. It remains backend-independent and does not
own PennyLane runtime execution.

`ansatz_analyzer` already owns metric computation, AnalysisResult collections,
Pareto/ranking/comparison transforms, tabular derived exports, optional
visualization APIs, and analyzer-owned PennyLane materialization through
`CircuitMaterializationConfig`, `MaterializedCircuit`,
`StateCallableProvider`, and `make_state_callable`.

`ansatz_evolver` already owns reference-first models, mutation policies and
requests, selection policies, AnalysisResult ingestion, EvolutionRun JSON
export, and event/reference records. It does not compute analyzer metrics or
run QNodes.

`workflow` already orchestrates public module boundaries, normalizes legacy
and structured stage declarations, prevents individual workflows from
evolving, supports artifact entry points, runs generic postprocessing, and can
continue or branch an EvolutionRun. It is still a large monolithic runner, and
the multi-generation transition loop is now driven through the public
evolver-owned `EvolutionStateMachine`, while workflow still owns artifact
routing and stage orchestration.

## Checkpoint 0 Finding

No immediate schema or scientific blocker was found at this audit checkpoint.
The current v0.3.2 schema/API surface appears compatible with additive v0.4.0
implementation:

- `evolution_run.schema.json` already has generation-level
  `analysis_result_refs` and `events`, closing the old Phase 6 blocker.
- `EvolutionRun` has metadata/configuration/event extension points sufficient
  for compatible patience, stopping, observability, and state-machine
  metadata.
- Workflow checkpointing can be introduced as a new durable workflow artifact
  without breaking existing canonical Candidate, AnalysisResult, or
  EvolutionRun documents.
- Materialization capabilities and limits can be added to analyzer public
  configuration/metadata without changing metric formulas.

Checkpoint 0 therefore passes as an implementation plan. All release-required
gaps below remain release-blocking if left unresolved before the final
candidate.

## Inventory Notes

### Mutation And Operators

Current productized execution includes the insert-only compatibility factory
and the campaign-neutral `CanonicalMutationFactory` for insert, replace,
remove, swap, reorder, and layer propagation. The evolver still schedules
generic mutation requests; generator-owned factories apply concrete operation
edits, preserve lineage, and return explicit valid/no-op or invalid outcomes.
Declarative workflow factory selection remains a later workflow configuration
task rather than a generator/evolver mutation blocker.

### Canonical Configuration

Workflow configuration is much better than the old Phase 10.0 audit: nested
`workflow.stages` is read, individual defaults no longer evolve, and
postprocessing includes visualization. Checkpoint 1 added declarative
stopping/patience governance under `evolver`, and Checkpoint 2 added
declarative `generation.constraints` with compatibility fingerprinting.
Remaining closure work is to make checkpointing, factory selection, manifests,
reports, and visualization profiles declarative and fingerprinted.

### Stage Semantics

The required vocabulary is present as scientific operations
`generate/analyze/evolve` and postprocessing aliases `rank/ranking`,
`visualize/visualization`. Dependency validation exists for missing analysis
inputs, individual evolution, comparison sources, and missing ranking/Pareto
metrics. The runner must still be decomposed so stages are explicit services
rather than one monolithic method.

### Materialization

Analyzer-owned materialization already computes tiny expressibility and
trainability when permissions and materialization are enabled. It correctly
keeps explicit metric callables as the highest-priority override and keeps
permission denial explicit. Checkpoint 4 added capability reporting,
configured materialization resource limits, limit metadata, and
machine-readable materialization failure reasons.

### Parallelism

Sequential remains safe and tested. Checkpoint 5 wires analyzer candidate-level
work to the core multiprocessing executor, keeps returned records in canonical
input order, rejects order-dependent `global_sequential` RNG under
multiprocessing, and raises explicit failures for worker or pickling errors
without sequential fallback. Workflow analysis stages inherit this behavior by
passing their execution config to `AnalysisPipeline`.

### Observability

Evolution events exist at generation granularity. Workflow provenance records
requested/executed operations and artifacts. There is no mid-run event sink,
deterministic JSONL event log, or observer failure policy.

### Checkpoint And Resume

EvolutionRun continuation and branch mode already preserve historical
generations and validate an evolution fingerprint. This is not yet production
workflow checkpointing: completed stages, RNG continuation state, atomic
checkpoint writes, and full input/config compatibility reports are missing.

### Exports And Manifest

Derived CSV/JSON writers exist for analysis, ranking, Pareto, and comparison.
WorkflowResult is an in-memory/printable manifest. v0.4.0 needs a persisted run
manifest and comprehensive deterministic traceability exports that include
lineage, selection, stopping, skipped metrics, and artifact hashes.

### Visualization

Visualization APIs are public, optional, and lazy-import Matplotlib. Workflow
can write generic plots. The frozen 25-plot publication contract must be
integrated as orchestration over public visualization APIs without redesign or
scientific recomputation.

### CLI

The CLI has only `run`. `validate` and `resume` are missing, and a report or
inspect command should be added only if backed by the deterministic report API.

### Deterministic Reports

No rule-based report layer exists. Reports should summarize factual canonical
run state and derived artifact locations, never unsupported scientific
interpretations.

### Public Examples And External Install

Existing CX01 and MIXT5G examples use public workflow APIs and no framework
campaign branches, but they still rely on example-local Python wrappers for
candidate preparation and factory injection. The final v0.4.0 proof must run
individual and evolutionary full-lite scientific workflows from an external
installation using config/public CLI/API only, with materialized expensive
metrics computing rather than reporting `"no state callable provided"`.

## Implementation Plan

The release plan can proceed without a scientific or schema redesign:

1. Implement TD-02/TD-03 stopping and patience first in `ansatz_evolver`, with
   compatibility-preserving defaults.
2. Propagate ConstraintSet through generator/evolver/workflow and fingerprints.
3. Complete generator-owned mutation factories for the campaign-neutral
   mutation families.
4. Harden analyzer materialization with capabilities, limits, and unsupported
   result metadata.
5. Integrate real fail-closed multiprocessing for scientific candidate work.
6. Move generation lifecycle transitions into an evolver-owned state machine.
7. Decompose WorkflowRunner into explicit stage executors.
8. Add atomic workflow checkpoint/resume.
9. Add structured observability and persisted event logs.
10. Add persisted manifests, deterministic exports, and traceability tables.
11. Integrate frozen publication visualization into workflow profiles.
12. Add deterministic report generation.
13. Expand the CLI to validate, run, resume, and optionally report.
14. Convert public examples to declarative full-lite scientific workflows.
15. Add reproducibility gates for sequential/parallel and uninterrupted/resume
    equivalence.
16. Perform architecture/dependency, documentation, and public API audits.
17. Update versioning only after all implementation and validation gates pass.

## Checkpoint 0 Decision

Checkpoint 0 is PASS.

No current schema or public API was found to make the v0.4.0 requirements
mutually incompatible. The implementation remains a productization and

## Checkpoint 1 Decision

Checkpoint 1 is PASS for TD-02 and TD-03.

Stopping and patience governance now live in `ansatz_evolver` policy/state
APIs, with workflow recording generation decisions, final stopping metadata,
and compatibility-preserving `patience=None` behavior. The checkpoint
validation recorded `261 passed, 1 warning`.

## Checkpoint 2 Decision

Checkpoint 2 is PASS for TD-04.

Constraint enforcement remains generator-owned: `ConstraintSet` performs
gate/connectivity checks, canonical Candidate export validates before emit,
and `InsertGateMutationFactory` validates inserted-gate intent and child
structure. Workflow now routes `generation.constraints` through generation,
loaded artifact validation, evolution child validation, persisted evolution
configuration, and evolution compatibility fingerprints so incompatible
constraint changes require an explicit branch. The checkpoint validation
recorded `267 passed, 1 warning`.

## Checkpoint 3 Decision

Checkpoint 3 is PASS for mutation/operator productization.

`CanonicalMutationFactory` now implements the supported mutation families
through the public CandidateFactory boundary, preserving deterministic
candidate IDs, root/parent/generation lineage, mutation metadata, no-op status,
constraint validation, and structural-dedup readiness. The compatibility
`InsertGateMutationFactory` remains available unchanged for insert-only
callers. The checkpoint validation recorded `273 passed, 1 warning`.

## Checkpoint 4 Decision

Checkpoint 4 is PASS for TD-07 and TD-08.

Analyzer-owned materialization now exposes `MaterializationCapability` through
`inspect_materialization_capability`, records configured limits in successful
materialization metadata, and fail-closes on configured qubit, operation, or
trainable-parameter limits with machine-readable pipeline metadata. Existing
disabled-materialization behavior and explicit metric-callable precedence are
preserved.

Checkpoint validation recorded `21 passed` for focused materialization tests,
`101 passed, 1 warning` for the broader analyzer suite, and
`277 passed, 1 warning` for full pytest.

## Checkpoint 5 Decision

Checkpoint 5 is PASS for TD-01.

Analyzer-owned candidate analysis now honors explicit
`execution.mode="multiprocessing"` by mapping candidate work through the core
executor and restoring results in canonical input order. Multiprocessing does
not fall back to sequential execution: core worker/pickling failures become
`ExecutionError`, analyzer failures become `AnalysisPipelineExecutionError`,
and worker-context failures retain candidate IDs without serializing traceback
internals. Expensive metrics with `rng_policy="global_sequential"` are rejected
under multiprocessing because their RNG contract is intentionally sequential.

Workflow analysis stages pass the configured execution policy to the analyzer,
including generated candidates. Direct `EvolverConfig` remains sequential-only
because the evolver does not execute analyzer metrics in this checkpoint.

Checkpoint validation recorded `19 passed` for focused core config/core
execution/analyzer/workflow multiprocessing contract tests,
`131 passed, 1 warning` for broader analyzer/workflow tests, and
`286 passed, 1 warning` for full pytest.

## Checkpoint 6 Decision

Checkpoint 6 is PASS for TD-10.

The evolver now exposes `EvolutionStateMachine` as the owner of legal
generation lifecycle transitions from initialization through planned/generated
candidates, analysis pending/complete, selection complete, checkpointed
generations, and terminal completed/failed/cancelled states.
`build_analyzed_generation_record` builds selection-complete
`GenerationRecord` objects by ingesting AnalysisResult references and recording
survivor, rejected, archive, stopping, and event metadata without importing
analyzer internals or executing metrics.

WorkflowRunner still owns artifact routing and analyzer execution, but its
generation-record, append, completion, and execution-metadata helpers delegate
to the public evolver state-machine boundary.

Checkpoint validation recorded `45 passed` for focused evolver
state-machine/workflow integration tests and `291 passed, 1 warning` for full
pytest.

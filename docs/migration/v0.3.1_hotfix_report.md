## Scope

v0.3.1 is a narrowly scoped correctness and contract-hardening hotfix. It does not introduce new scientific semantics and does not begin the v0.4.0 architecture work.

The release goal is that v0.3.x does exactly what it claims to do, with truthful metadata, provenance, capability claims, and expected runtime errors.

## Explicit Non-goals

The following were intentionally not implemented: WorkflowRunner integration of stopping policies, patience behavior, transversal constraints, real scientific multiprocessing, general backend capabilities, a derived-expression evaluator, new PennyLane gate adapters, a general GateRegistry-to-materializer plugin system, turnkey subtract/replace/permutation mutation factories, unified EvolverConfig/EvolutionStageConfig, Evolver state-machine migration, WorkflowRunner decomposition, publication-suite auto orchestration, full CSV export, workflow/run manifest redesign, interpreters, automatic scientific reports, mid-run feedback/event observers, checkpoint redesign, CLI redesign, arbitrary external CSV ingestion, and changes to independent multithreshold trajectory semantics.

## HOTFIX-02 - Workflow Provenance Correctness

Status: FIXED

Source evidence before:

- Workflow provenance could report `plots_generated_by_runner = false` even when the WorkflowRunner produced visualization files.
- Existing flags distinguished multiple execution layers but the direct-runner meaning of some fields was underdocumented.

Change made:

- `WorkflowRunner` now sets `plots_generated_by_runner` from the actual visualization output paths.
- Existing keys were preserved.
- `docs/architecture/workflow_runner.md` now documents that direct-runner flags mean work directly performed by WorkflowRunner, not delegated analyzer QNode execution.

Tests added:

- `tests/test_workflow_phase_10_4_postprocessing.py` assertions for visualization-positive workflows.
- `tests/test_workflow_phase_10_4_postprocessing.py` assertions for postprocessing workflows without visualization.
- `tests/test_workflow_runner.py` minimal workflow assertion that `plots_generated_by_runner` remains false when no visualization is requested.

Compatibility impact:

- Existing provenance keys remain present.
- The corrected value removes a contradiction for visualization workflows.
- Scientific provenance semantics are unchanged.

## HOTFIX-03 - CLI Optional-dependency Failure Handling

Status: FIXED

Source evidence before:

- The visualization layer raised `VisualizationDependencyError` when Matplotlib was unavailable.

Change made:

- Python/API behavior outside the CLI remains unchanged.

Tests added:

Compatibility impact:

- Expected optional-dependency failures become user-facing CLI errors.

## HOTFIX-04 - Multiprocessing Capability Honesty

Status: FIXED

Source evidence before:

- Core exposed `ExecutionConfig(mode="multiprocessing")`, `MultiprocessingExecutor`, and `build_executor()`.
- Candidate-level scientific pipelines did not consume that executor and were effectively sequential.
- Public scientific entry points could therefore appear to accept multiprocessing while executing sequentially.

Change made:

- Core executor primitives remain available.
- Added shared message `SCIENTIFIC_MULTIPROCESSING_DEFERRED_MESSAGE`.
- Direct analyzer configuration rejects non-sequential scientific execution.
- `WorkflowRunner` rejects multiprocessing before scientific work when scientific execution is requested.
- `EvolverConfig` rejects non-sequential execution rather than making a false capability claim.
- Postprocessing-only workflows remain allowed because they do not execute candidate science.
- Current architecture and user docs now distinguish core executor primitive availability from scientific workflow backend support.

Tests added:

- `tests/test_hotfix_v031_contracts.py::HotfixV031ContractTests::test_direct_analyzer_rejects_scientific_multiprocessing`
- `tests/test_hotfix_v031_contracts.py::HotfixV031ContractTests::test_workflow_rejects_multiprocessing_before_scientific_work`
- `tests/test_hotfix_v031_contracts.py::HotfixV031ContractTests::test_evolver_config_rejects_scientific_multiprocessing_claims`
- `tests/test_hotfix_v031_contracts.py::HotfixV031ContractTests::test_sequential_workflow_execution_still_runs`

Compatibility impact:

- Sequential scientific execution is unchanged.
- Configurations that requested scientific multiprocessing now fail early and truthfully instead of silently running sequentially.

## HOTFIX-05 - Candidate to PennyLane Materialization Contract Honesty

Status: FIXED

Source evidence before:

- Candidate JSON can represent derived parameters.
- Current PennyLane materialization cannot materialize derived parameters.
- Candidate operation gates include name, namespace, and version.
- `OperationView` preserved gate name but discarded namespace/version.
- Built-in canonical generator output uses the `verfeinert.default_gates` namespace.
- The materializer supports a fixed built-in gate set, not arbitrary GateRegistry semantics.

Change made:

- `OperationView` now preserves `gate_namespace` and `gate_version` additively.
- The PennyLane materializer supports legacy omitted namespaces and `verfeinert.default_gates` without gate versions.
- Unknown namespaces and explicit gate versions fail closed with `CircuitMaterializationError`.
- Derived parameters remain representable but fail with a clear v0.3.1 materialization error.
- Non-numeric literal/runtime parameter forms fail with clear `CircuitMaterializationError` messages.

Tests added:

- `tests/test_ansatz_analyzer_phase_10_1_materialization.py::test_built_in_candidate_fixture_materializes_with_default_namespace`
- `tests/test_ansatz_analyzer_phase_10_1_materialization.py::test_derived_parameter_is_representable_but_not_materializable`
- `tests/test_ansatz_analyzer_phase_10_1_materialization.py::test_unsupported_gate_namespace_is_not_matched_by_name`
- `tests/test_ansatz_analyzer_phase_10_1_materialization.py::test_unsupported_gate_version_is_not_matched_by_name`
- `tests/test_ansatz_analyzer_phase_10_1_materialization.py::test_non_numeric_literal_parameter_fails_clearly`

Compatibility impact:

- Existing built-in Verfeinert candidates remain materializable.
- Ambiguous or unsupported semantic gate identities are rejected instead of being interpreted by name alone.
- No schema expressiveness was removed.
- No general backend capability framework was introduced.

## HOTFIX-07 - jsonschema RefResolver Deprecation

Status: FIXED

Decision and rationale:

- Migrated production validators from legacy `jsonschema.RefResolver` to `referencing.Registry` because the change was small, centralized, and covered by existing schema-contract tests plus focused reruns.
- Added direct dependency floors `jsonschema>=4.18` and `referencing>=0.30`.
- Kept packaged schema loading and local schema URI behavior intact through `verfeinert.core.schema_resources.schema_registry()`.
- No schema redesign was performed.

Source evidence before:

- Production validators imported or constructed `RefResolver` in analyzer validation, analyzer comparison validation, evolver validation, and staged-package export validation.
- Tests also used resolver-oriented validation helpers.

Change made:

- Added `schema_registry()` in `verfeinert/core/schema_resources.py`.
- Updated production validators to pass `registry=...` to `Draft202012Validator`.
- Updated schema tests to use the same modern registry path.
- Verified `rg -n "RefResolver|resolver=" verfeinert tests` returns no matches.

Tests added/updated:

- `tests/test_ansatz_generator_schema_contract.py`
- `tests/test_data_model_schemas.py`
- Existing analyzer/evolver/workflow validation suites were rerun.

Compatibility impact:

- Validation behavior and packaged schema resolution are preserved.
- Deprecation-warning surface is reduced.
- Accepted/rejected scientific documents were not intentionally changed.
